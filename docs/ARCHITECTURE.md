# Архитектура проекта

## 1. Общая схема

Архитектура проекта построена на разделении исходных, подготовленных и аналитических данных.

```text
                 ИСТОЧНИКИ
  Steam / RAWG / Epic / Twitch / YouTube / Habr
                       |
                       v
                  raw/
          исходные данные без изменений
                       |
                       v
                ПРОВЕРКА КАЧЕСТВА
       структура / типы / пропуски / дубликаты
                       |
                       v
                 processed/
             очищенные данные Parquet
                       |
                       v
                  DuckDB
           интеграция и аналитические
                 представления
                       |
                       v
            статистический анализ
              и визуализация
```

## 2. Слой raw

Каталог `raw/` предназначен для хранения исходных файлов.

Принципы:

- исходные данные не перезаписываются результатами очистки;
- структура источника по возможности сохраняется;
- для новых источников фиксируется дата получения;
- API-ответы сохраняются в исходном JSON;
- секретные ключи и токены не сохраняются в репозитории.

## 3. Слой processed

Каталог `processed/` содержит подготовленные наборы данных.

Основной формат — Parquet.

Преимущества:

- колоночное хранение;
- эффективное чтение отдельных столбцов;
- сжатие;
- совместимость с DuckDB и PyArrow;
- возможность обработки больших наборов без полной загрузки в pandas.

Примеры:

- `processed/games/steam_games.parquet`;
- `processed/games/rawg_games.parquet`;
- `processed/games/epic_games.parquet`;
- `processed/players/steam_monthly_players.parquet`;
- `processed/twitch/twitch_games.parquet`;
- `processed/youtube/youtube_videos.parquet`;
- `processed/text/habr_articles.parquet`.

## 4. Аналитическое хранилище

Для аналитической интеграции используется DuckDB.

DuckDB позволяет выполнять SQL-запросы непосредственно к Parquet-файлам и формировать аналитические представления.

Предполагаемые сущности:

- `dim_game` — справочник игр;
- `fact_players` — активность игроков во времени;
- `fact_reviews` — отзывы и оценки;
- `fact_recommendations` — рекомендации;
- `fact_twitch` — статистика просмотров и трансляций;
- `fact_youtube` — статистика видеороликов.

Физическая схема уточняется по результатам проверки ключей и совместимости источников. Нельзя считать названия игр надёжным универсальным ключом без проверки.

## 5. Интеграция

Приоритет ключей:

1. идентификатор платформы, если оба источника относятся к одной платформе;
2. подтверждённое соответствие внешних идентификаторов;
3. нормализованное название игры;
4. дополнительная проверка даты выхода и разработчика.

Для нормализации названий:

- перевод в нижний регистр;
- удаление лишних пробелов;
- унификация знаков пунктуации;
- удаление технических различий в написании, если это не меняет название.

Автоматическое совпадение по названию рассматривается как кандидат на объединение, а не как безусловное доказательство идентичности.

## 6. Неструктурированные данные

Тексты Habr и метаданные YouTube проходят отдельный процесс подготовки:

- извлечение текста и метаданных;
- удаление технических элементов;
- нормализация текста;
- токенизация;
- векторизация TF-IDF.

Векторизация применяется для представления текстов в числовом виде. Она не означает применение модели машинного обучения для предсказания популярности.

## 7. Обновление данных

Повторный сбор должен:

- сохранять исходные ответы;
- не дублировать уже загруженные записи;
- фиксировать дату сбора;
- сохранять идентификаторы источника;
- позволять повторно построить подготовленные Parquet-наборы.

Для API-источников необходимо учитывать ограничения квоты и кэшировать ранее полученные ответы.
