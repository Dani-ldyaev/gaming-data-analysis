# Архитектура проекта

## 1. Общая схема

Архитектура проекта построена на разделении исходных, подготовленных и аналитических данных.

```text
                  ИСТОЧНИКИ
 Steam / RAWG / Epic / Twitch / YouTube / Habr / Wikidata
                         |
                         v
                     raw/
            исходные данные без изменений
                         |
                         v
                ПРОВЕРКА КАЧЕСТВА
        структура / типы / пропуски / дубликаты
                         |
                         v
                   processed/
             очищенные данные Parquet
                         |
                         v
                     DuckDB
             интеграция и аналитические
                   представления
                         |
                         v
              статистический анализ
                  и визуализация
```

## 2. Слой raw

Каталог `raw/` предназначен для хранения исходных файлов.

Принципы:

- исходные данные не перезаписываются результатами очистки;
- структура источника по возможности сохраняется;
- для новых источников фиксируется дата получения;
- API-ответы сохраняются в исходном формате;
- XML-ответы сохраняются как исходные XML-документы;
- секретные ключи и токены не сохраняются в репозитории;
- повторный запуск не должен приводить к случайному удалению ранее полученных данных.

Основные группы:

```text
raw/
├── steam/
│   ├── fronkongames/
│   ├── recommendations/
│   ├── monthly_players/
│   └── reviews/
│
├── rawg/
├── epic/
├── twitch/
│   ├── evolution/
│   └── streamers/
│
├── youtube/
├── habr/
└── xml/
    └── wikidata/
```

Фактическая структура каталогов определяется реально полученными файлами. Наличие каталога в схеме не означает, что все перечисленные источники уже обработаны.

## 3. Слой processed

Каталог `processed/` содержит подготовленные наборы данных.

Основной формат — Parquet.

Преимущества:

- колоночное хранение;
- эффективное чтение отдельных столбцов;
- сжатие;
- совместимость с DuckDB и PyArrow;
- возможность обработки больших наборов без полной загрузки в pandas.

Целевая структура:

```text
processed/
├── games/
│   ├── steam_games.parquet
│   ├── rawg_games.parquet
│   ├── epic_games.parquet
│   ├── wikidata_games.parquet
│   └── game_source_mapping.parquet
│
├── players/
│   └── steam_monthly_players.parquet
│
├── recommendations/
│   ├── steam_recommendations.parquet
│   ├── steam_recommendation_games.parquet
│   └── steam_users.parquet
│
├── reviews/
│   └── steam_reviews_sample.parquet
│
├── twitch/
│   ├── twitch_games.parquet
│   └── twitch_streamers.parquet
│
├── youtube/
│   └── youtube_videos.parquet
│
└── text/
    ├── habr_articles.parquet
    └── tfidf/
```

Данная структура является целевой. Фактическое наличие файлов подтверждается инвентаризацией в ноутбуке 2.3.

## 4. Аналитическое хранилище

Для аналитической интеграции используется DuckDB.

DuckDB позволяет выполнять SQL-запросы непосредственно к Parquet-файлам и формировать аналитические представления.

Предполагаемые сущности:

- `dim_game` — справочник игр;
- `fact_players` — активность игроков во времени;
- `fact_reviews` — пользовательские отзывы и оценки;
- `fact_recommendations` — рекомендации;
- `fact_twitch` — статистика просмотров и трансляций;
- `fact_youtube` — статистика видеороликов;
- `fact_wikidata` — дополнительные характеристики игр из Wikidata.

Физическая схема уточняется по результатам проверки ключей и совместимости источников. Нельзя считать названия игр надёжным универсальным ключом без проверки.

## 5. Интеграция источников

Для объединения данных разных платформ используется отдельная таблица соответствий `game_source_mapping`.

Предполагаемые поля:

| Поле | Назначение |
|---|---|
| `canonical_game_id` | Внутренний идентификатор игры |
| `source_name` | Название источника |
| `source_game_id` | Идентификатор игры в конкретном источнике |
| `source_game_name` | Исходное название |
| `normalized_name` | Нормализованное название |
| `match_method` | Метод сопоставления |
| `match_status` | Статус проверки |

Идентификаторы источников:

- Steam — `appid` / `AppID`;
- RAWG — `id`;
- Wikidata — `wikidata_id`;
- YouTube — `video_id` для видеоролика, а не игры;
- Twitch — название игры в доступных наборах данных.

Идентификаторы разных платформ не являются взаимозаменяемыми.

Приоритет сопоставления:

1. подтверждённый общий идентификатор;
2. проверенное соответствие внешних идентификаторов;
3. точное совпадение нормализованных названий;
4. дополнительная проверка даты выхода, разработчика и других характеристик.

Автоматическое совпадение по названию рассматривается как кандидат на объединение, а не как безусловное доказательство идентичности.

Неоднозначные совпадения должны сохраняться для отдельной проверки. Если надёжное сопоставление невозможно, запись остаётся несопоставленной.

## 6. Обработка неструктурированных данных

Текстовые данные представлены несколькими типами документов:

- пользовательские отзывы Steam;
- публикации Habr;
- заголовки и описания видеороликов YouTube.

Эти типы документов не смешиваются без сохранения информации об источнике.

Этапы подготовки:

1. извлечение текста;
2. удаление технических элементов и HTML-разметки;
3. нормализация;
4. токенизация;
5. лемматизация или стемминг при необходимости;
6. формирование текстовых признаков;
7. TF-IDF-векторизация;
8. сохранение результатов и параметров обработки.

Для больших массивов отзывов допускается использование воспроизводимой выборки.

Векторизация применяется для представления текстов в числовом виде и последующего описательного анализа. Она не означает построение предсказательной ML-модели.

## 7. Обработка XML

XML-источник представлен выгрузкой из Wikidata Query Service.

Исходный XML сохраняется в:

`raw/xml/wikidata/wikidata_video_games.xml`.

В процессе подготовки:

- проверяется корректность XML;
- извлекаются вложенные элементы результата SPARQL;
- формируются табличные записи;
- преобразуются даты и числовые характеристики;
- проверяются пропуски и дубликаты;
- результат сохраняется в Parquet.

Исходный XML остаётся неизменным и используется как воспроизводимый источник данных.

## 8. Контроль качества

Для каждого источника проверяются:

- количество строк и столбцов;
- типы данных;
- количество пропусков;
- количество дубликатов;
- уникальность идентификаторов;
- корректность дат;
- диапазоны числовых характеристик;
- заполненность категориальных признаков.

Для интеграции дополнительно проверяются:

- количество сопоставленных игр;
- количество несопоставленных записей;
- неоднозначные совпадения;
- отсутствие нежелательного размножения строк при объединении.

Итоговые отчёты сохраняются в `docs/data_quality/`.

## 9. Обновление данных

Повторный сбор должен:

- сохранять исходные ответы;
- не дублировать уже загруженные записи;
- фиксировать дату сбора;
- сохранять идентификаторы источника;
- позволять повторно построить подготовленные Parquet-наборы;
- не перезаписывать корректные результаты частично загруженными данными.

Для API-источников необходимо учитывать ограничения квоты и кэшировать ранее полученные ответы.

## 10. Разделение существующих и планируемых данных

Ранее подготовленные Parquet-наборы не следует автоматически считать результатами нового этапа 2.3.

К подтверждённым ранее существовавшим наборам относятся:

- `processed/games/epic_games.parquet`;
- `processed/games/rawg_games.parquet`;
- `processed/games/steam_games.parquet`;
- `processed/players/steam_monthly_players.parquet`;
- `processed/twitch/twitch_games.parquet`.

Их актуальность, структура и качество повторно проверяются в 2.3.

Новые наборы, включая `wikidata_games.parquet`, `steam_reviews_sample.parquet`, `youtube_videos.parquet` и `game_source_mapping.parquet`, считаются результатами обработки только после фактического создания и проверки соответствующих файлов.
